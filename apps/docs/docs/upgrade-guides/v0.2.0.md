# v0.2.0

v0.2.0 is a major release. The backend was rewritten from FastAPI to Django,
the object-storage and database layers became fully pluggable, and the
client-side crypto moved to **Scheme v3**. Most of the change is invisible in
the browser, but the upgrade path has a few hard requirements — the most
important being that **files shared before v0.2.0 can no longer be opened**
(see [Cryptography](#cryptography-scheme-v3-is-a-breaking-change) below).

## Installation

Update your `chithi` to the latest version using docker compose.

Inside your docker compose directory for the chithi deployment:

```shell
docker compose pull
```

Then:

```shell
docker compose up -d
```

The backend now runs its own database migrations automatically at boot
(`python manage.py migrate`), so no manual migration step is required when the
database is SQLite or Postgres.

## Breaking changes

### The backend is now Django, and the API is GraphQL

The v0.1.x backend was a FastAPI + SQLAlchemy service. v0.2.0 replaces it with
Django, exposing the same contract over two transports:

- **django-ninja REST** (`/api/...`) — request/response endpoints, and
- **Strawberry GraphQL** (`/graphql/`) — the same operations as queries/mutations.

Upload and download are public by default; when an instance requires
authentication, an access token is obtained via the `login`/`register` GraphQL
mutations and sent as `Authorization: Bearer <access-token>`.

There is **no compatibility shim**: clients written against the old v0.1.x
routes will not work unchanged. The official web frontend and CLI shipped with
v0.2.0 speak the new API. If you have built a
[custom client](../backend/custom-clients.md), update it to the new endpoints
and the chunked upload/download protocol before upgrading.

### Environment variables were renamed

The v0.2.0 backend reads a different set of environment variables. The most
common renames, for anyone who previously set these by hand:

| v0.1.x (FastAPI)       | v0.2.0 (Django)        | Notes                                    |
| :--------------------- | :--------------------- | :--------------------------------------- |
| `POSTGRES_SERVER`/`POSTGRES_PORT`/`POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` | `DATABASE_URL` | A single connection string (see [Database backends](../backend/database.md)). SQLite is now the zero-config default. |
| `RUSTFS_ENDPOINT_URL`  | `S3_ENDPOINT_URL`      | Object storage is now configured via the generic S3 surface (see [Storage backends](../backend/storage.md)). |
| `RUSTFS_ACCESS_KEY`    | `S3_ACCESS_KEY_ID`     |                                            |
| `RUSTFS_SECRET_ACCESS_KEY` | `S3_SECRET_ACCESS_KEY` |                                          |
| `REDIS_ENDPOINT`       | — (removed)            | The old separate general-purpose Redis slot is gone; the Celery broker URL doubles as the cache and channel layer. |

`SECRET_KEY` (Django signing key) is a **new required variable**. Set it to a
long random string in your compose file / secrets manager before first boot.

The full list is in [Environment](../backend/environment.md).

### Database and storage are now pluggable

Where v0.1.x was hard-wired to Postgres + RustFS, v0.2.0 defaults to **SQLite**
for the database and the **local filesystem** for storage, and lets you point
either at a managed backend with two variables:

- Database — `DATABASE_URL` (SQLite, PostgreSQL, or MySQL/MariaDB).
- Storage — `STORAGE_BACKEND` (`local`, `s3`, `gcs`, `azure`, `openstack`)
  plus the matching credentials.

See [Database backends](../backend/database.md) and
[Storage backends](../backend/storage.md).

!!! tip

    If you previously ran RustFS as your object store, map it to the `s3`
    backend: point `S3_ENDPOINT_URL` at the RustFS endpoint, set
    `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` to your RustFS keys, and set
    `S3_BUCKET_NAME`. Existing chunks stored by a v0.1.x instance remain
    readable — the object-storage layout (per-file chunk objects) is
    unchanged.

### Cryptography: Scheme v3 is a breaking change

The client-side encryption was upgraded to **Scheme v3**
(AES-256-GCM + Argon2id + a real per-file salt). See the
[Cryptography Architecture](../crypto-architecture.md) page for the full
scheme.

!!! danger

    **Ciphertexts produced under v3 cannot be decrypted by v0.1.x code, and
    files shared under v0.1.x cannot be opened after upgrading to v0.2.0.**
    There is no back-compatibility shim.

    In practice this means: **any file a user shared before upgrading will
    become unreadable once the v0.2.0 frontend / CLI is deployed.** Share-URLs
    that were already distributed will stop working after the upgrade.

    If you need to preserve access to previously shared files, download them
    with a v0.1.x client *before* upgrading. After upgrading, only files
    shared *after* the upgrade (which use Scheme v3) will open.

The two official clients (web and CLI) are byte-compatible with each other and
both implement Scheme v3, so they remain interoperable.

### Frontend still requires COOP and COEP headers

As introduced in v0.1.0, the frontend performs in-browser work (image
transcoding, 7z archive handling) using WebAssembly threads, which requires
[COOP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Opener-Policy)
and [COEP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Embedder-Policy)
headers. Your reverse proxy must continue to add them.

If you are already serving the v0.1.x frontend correctly, nothing changes —
just keep the headers in place. If you are upgrading a reverse proxy config,
see the [Deployments](../deployments/docker/basic/caddy.md) section for your
reverse proxy of choice.

## Non-breaking changes

- **Django admin** is available at `/admin/` when `DEBUG` is on, for inspecting
  config, files, and auth users directly.
- **Deferred-annotations** and other backend internal refactors; no API
  surface impact beyond what is listed above.
- **Celery beat** is optional. The single scheduled job (file expiry cleanup)
  uses Celery `countdown`/`eta`, so a running worker is sufficient; beat is
  only needed if you add periodic tasks.

## Rollback

Rolling back to v0.1.x is possible for the *application*, but note that any
files shared while running v0.2.0 (Scheme v3) will **not** open under a v0.1.x
client. If you must roll back, you lose access to post-upgrade shares the same
way.

```shell
# Point compose at the previous image tag, then:
docker compose up -d
```

Database schema changes made by v0.2.0 migrations are not auto-reverted by
rolling back the image; if you changed the schema, restore the database from a
pre-upgrade backup before rolling the image back.
